# WebAPI — план реализации

**Статус** — реализация WebAPI выполнена. В локальном Release-прогоне с MongoDB replica set и RabbitMQ прошли 72 теста без пропусков. [Команды запуска](../docs/webapi-testing.md)

**Комплект для исполнителя:** этот файл + `plan/README.md`. Это план уже выполненного этапа и справка для поддержки, а не указание создать второй WebAPI. Общие C#-контракты, точные HTTP-снимки, календарь, настройки транспорта и команды тестовой инфраструктуры приведены в README. Для точного изменения существующих исходников потребуется репозиторий или соответствующие файлы; по двум документам можно подготовить решение и проверки, но нельзя достоверно переписать невидимый контроллер.

**Цель** — расширить существующее API настройками напоминаний и сводки, обеспечить надёжную публикацию изменений для Worker.

**Основа** — [архитектура](README.md), [контракты RabbitMQ](04-rabbitmq.md), [существующие API и модели](../Auth/WebApplication1/).

## Настройки и публичные маршруты

| Метод и маршрут | Действие |
|---|---|
| `GET /api/habits/{id}/reminder` | Вернуть настройки напоминания владельцу привычки |
| `PUT /api/habits/{id}/reminder` | Заменить настройки напоминания и вернуть сохранённые значения |
| `GET /api/profile/summary-settings` | Вернуть настройки ежедневной сводки текущего пользователя |
| `PUT /api/profile/summary-settings` | Заменить настройки сводки и вернуть сохранённые значения |

У всех четырёх маршрутов ответ `200` с `{ "enabled": false, "localTime": "20:00" }` для напоминания или соответствующим временем сводки. `PUT` принимает оба поля. Время имеет формат `HH:mm`, диапазон `00:00`–`23:59`. Новые и существующие записи по умолчанию выключены, время напоминания `20:00`, сводки `21:00`. Настройки хранятся внутри документов привычки и пользователя. Календарные правила используют действующий часовой пояс аккаунта, по умолчанию `Asia/Yekaterinburg`.

Требовать JWT и валидный `sub`. Для чужой или отсутствующей привычки вернуть `404`, для изменения архивной привычки — `409`, для некорректного тела — `400`. Проверять владельца в фильтре MongoDB. Существующие маршруты и тела ответов сохраняются.

## Внутренние маршруты Worker

Доступ через `X-Worker-Key` с секретом `WorkerApi__SharedKey`, сравниваемым в постоянное время. Внешний ingress маршрутизирует `/api` и `/hubs`, а `/internal` доступен Worker через ClusterIP и сетевую политику. Ключ не записывается в логи.

| Метод и маршрут | Контракт |
|---|---|
| `GET /internal/v1/habit-schedules?after={id}&limit=100` | Страница полных снимков привычек по возрастанию ObjectId, включая выключенные и архивные, ответ `{ items, nextCursor }` |
| `GET /internal/v1/summary-schedules?after={id}&limit=100` | Страница настроек сводки с версией по ObjectId пользователя |
| `GET /internal/v1/users/{userId}/habits/{habitId}/reminder?date=YYYY-MM-DD` | `{ eligible, habitName, revision }`. Учитывает настройки, состояние, расписание, дату пользователя и отметку |
| `GET /internal/v1/users/{userId}/summary?date=YYYY-MM-DD` | `{ eligible, planned, completed, pending, revision }`. Считает активные привычки, запланированные на эту местную дату, через правила `HabitService` |

Снимки используют поля контрактов [RabbitMQ](04-rabbitmq.md) без транспортных метаданных. Для `limit` допустим диапазон `1..200`. Отсутствующая сущность возвращает `404`. Если проверяемая дата отличается от текущей местной даты, настройки выключены или привычка уже выполнена, архивирована либо вне расписания, вернуть `eligible: false`. Если все остальные условия выполнены, а срок в тот же день ещё не наступил, вернуть `eligible: false`, `reason: "notDueYet"` и `nextDueAtUtc`. WebAPI и Worker используют общий расчёт срока в UTC, включая переходы DST из [плана Worker](02-worker.md). Сводка допустима и при нуле запланированных привычек. Чтение привычек и отметок для одного вычисления проводить в согласованном снимке MongoDB.

## Тесты по этапам

- [x] **Контракты.** Тест сериализации проверяет обязательные поля трёх сообщений. Интеграционный тест публикации WebAPI проверяет передачу `MessageId`, `CorrelationId` и контекста трассировки.
- [x] **Настройки и совместимость.** Модульные тесты проверяют формат времени. HTTP-тесты проверяют значения по умолчанию для старых документов, `401` без JWT, `404` для чужой привычки, `409` для архива, `400` для неверного времени, повтор `PUT` и сохранение настроек после входа.
- [x] **Запись изменений и outbox.** Интеграционные тесты на replica set проверяют, что каждый фактический переход записывает состояние и событие с новой версией, а повтор команды сохраняет прежнюю версию и число событий. Ошибка записи события откатывает изменение данных.
- [x] **Публикация.** Интеграционный тест с реальным RabbitMQ считывает оба события из `worker-habit-events-v1` после публикации при отсутствии активного потребителя. При недоступности брокера API сохраняет изменение. После подтверждения публикации и сбоя до обновления outbox запись выходит из lease и публикуется с исходным `eventId`.
- [x] **Внутренние маршруты.** HTTP-тесты проверяют ключ, пагинацию, местную дату, выключенные настройки, расписание, отметку, архив, перенос срока и сводку без привычек.
- [x] **Ошибки и индексы.** HTTP-тесты подтверждают действующие `code` и статусы ошибок, а при неожиданном исключении — `500` с `traceId` и без деталей. Интеграционный тест дважды запускает инициализацию и сверяет уникальность и состав индексов в MongoDB.

## Инварианты при последующих изменениях

1. Любое фактическое изменение привычки увеличивает `Habit.Revision` и при включённой функции записывает полный `HabitChangedV1` той же версии. Изменение отметки — тоже изменение агрегата. Повтор команды без изменения данных не создаёт новую revision/outbox.
2. Настройки сводки используют отдельную `SummaryRevision`, а не revision произвольной привычки. Регистрация и вход не заменяют пользовательский документ устаревшей копией, стирающей настройки.
3. Для события взять актуальный timezone владельца; название привычки в `HabitChangedV1` отсутствует по контракту. Worker получает название в момент eligibility, добавлять несовместимое обязательное поле в v1 не требуется.
4. Состояние, revision и outbox коммитятся вместе; ошибка Insert outbox откатывает состояние. Общий publisher работает после commit и не вызывается синхронно из контроллера.
5. Пагинация включает выключенные и архивные записи; одно вычисление eligibility читает согласованный снимок MongoDB. Нельзя заменить два чтения одной проверки произвольными независимыми запросами без snapshot.
6. Результат `eligible=false` обычно не раскрывает причину; исключение `notDueYet` с корректным `nextDueAtUtc`. Смена времени 20:00 → 21:00 должна переносить старое задание. Сводка 0/0/0 остаётся допустимой.
7. Четыре новых публичных маршрута отсутствуют при `Features__NotificationsEnabled=false`. Обычный CRUD продолжает работать; новые outbox-записи отключены, существующие не удаляются. Это не глобальный stop всей распределённой системы.
8. Не менять существующие статусы/code привычек ради новой глобальной обработки ошибок. JWT sub должен быть ObjectId; owner-фильтры остаются в БД. Ключ Worker не логируется и не становится заменой сетевой изоляции.

## Как проверить изменение этого этапа

Использовать [команды запуска тестового стенда](../docs/webapi-testing.md), затем `dotnet test Auth/WebApplication1.sln -c Release -m:1 --logger trx`. Последовательный запуск позволяет пройти сценарию WebAPI, который временно блокирует AMQP-подключения в тестовом vhost. Сверить число выполненных интеграций и пропусков.

Для целевой регрессии сначала воспроизвести поведение отдельным тестом: например, ошибка outbox не оставляет новое время, чужой пользователь получает 404, две одинаковые отметки дают одну запись, событие на vN содержит состояние именно vN. Затем прогнать затронутый набор и весь backend. Тесты RabbitMQ используют только выделенный брокер, потому что могут временно запрещать подключения к vhost.

Для ingress недостаточно получить любой 404/401: внешний запрос `/internal/v1/habit-schedules` не должен вообще попасть в upstream WebAPI. Проверить правила и журнал прокси; внутри сети с ключом запрос работает. Для CI приложить ссылку на фактически успешный run. До этих проверок две галочки выше оставить пустыми.

**Сдача дальнейшей правки:** изменение исходников и регрессионный тест, соответствующие поправки README/HTTP-контракта при необходимости, результаты запуска. При несовместимом изменении внешнего контракта остановить одностороннее внедрение и согласовать версию с Worker/Notifications.
