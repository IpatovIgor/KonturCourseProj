# Notifications и React — план реализации

**Цель** — сохранять уведомления и доставлять их нужному пользователю через SignalR. Пользователь может восстановить пропущенные сообщения через историю.

**Основа** — [архитектура](README.md), [событие `NotificationReadyV1`](04-rabbitmq.md), [клиент React](../habit-frontend/src/). Создать `Auth/HabitTracker.Notifications` на ASP.NET Core .NET 8.

## Контракты для клиента

| Маршрут или событие | Контракт |
|---|---|
| `GET /api/notifications?limit=20&cursor={cursor}` | `{ items, nextCursor, unreadCount }`. `limit` от 1 до 100. Сортировка по `createdAtUtc` и ID по убыванию. Курсор кодирует оба поля последнего элемента |
| `PUT /api/notifications/{id}/read` | `204` при отметке и её повторе. `404` для отсутствующего или чужого уведомления |
| `/hubs/notifications` | Защищённое подключение SignalR. Серверное событие `NotificationReceived` содержит один DTO уведомления |

DTO содержит `id`, `kind`, `localDate`, `createdAtUtc`, `readAtUtc` и поля полезной нагрузки по виду уведомления. Напоминание передаёт `habitId` и `habitName`, сводка — `planned`, `completed`, `pending`. Текст формируется во фронтенде из этих полей. `unreadCount` относится ко всем уведомлениям владельца.

## Шаги

- [ ] Зарегистрировать JWT Bearer с параметрами WebAPI и `MapInboundClaims = false`. Проверять подпись, срок, issuer, audience и формат `sub`. Зарегистрировать `IUserIdProvider` по `sub`. Для браузерного SignalR принимать `access_token` из query string только на `/hubs/notifications`. Закрывать соединение по истечении токена. Применить редактирование URL в логах сервиса, прокси и телеметрии.
- [ ] Добавить репозиторий `notifications`. `_id` — `notificationId`, `userId` — владелец. Индекс `(userId, createdAtUtc, _id)` обслуживает историю. Индекс `(userId, readAtUtc)` обслуживает счётчик. Отметка прочтения выставляет `readAtUtc` один раз с фильтром по владельцу и ID.
- [ ] Подключить общие контракты и MassTransit consumer `NotificationReadyV1` на `notifications-ready-v1`. Применить политику retry, `_error` и `_skipped` из [спецификации RabbitMQ](04-rabbitmq.md#потребители-и-очереди-ошибок). Выполнить upsert с `$setOnInsert`, затем отправить сохранённый DTO через `IHubContext` в `Clients.User(userId)`. Подтверждать обработку после успешной записи и вызова SignalR. Ошибка отправки вызывает retry, повторная доставка использует тот же ID. Для пользователя без активного подключения запись остаётся доступной через REST.
- [ ] Добавить REST-маршруты, глобальную обработку исключений и валидацию курсоров. Все запросы к хранилищу включают `sub` из токена. Hub предоставляет только серверные уведомления, пользовательские RPC для отправки отсутствуют.
- [ ] В React добавить `@microsoft/signalr`, панель уведомлений, счётчик и настройку сводки. Настройку напоминания разместить на странице привычки и сохранить отдельным запросом. После создания привычки дать возможность включить напоминание по её ID. При ошибке сохранения настройки показывать состояние привычки и возможность повторить настройку.
- [ ] Регистрировать `NotificationReceived` до запуска соединения. Использовать `accessTokenFactory`, переподключение после потери связи и повтор начального подключения при временном сбое. После первого подключения и каждого переподключения загрузить историю. Объединять элементы по ID, сохраняя `readAtUtc` при повторе. Обновлять серверный счётчик при загрузке, прочтении и новом событии, объединяя близкие запросы и игнорируя устаревшие ответы. При выходе отменять запросы, останавливать соединение и очищать историю сеанса.
- [ ] Направить `/api/notifications` и `/hubs/notifications` на Notifications в Vite и ingress. Для Hub включить проксирование WebSocket. На первом стенде запустить одну реплику Notifications со стратегией `Recreate`. Клиенты восстанавливают историю после её перезапуска.

## Тесты по этапам

- [ ] **JWT и Hub.** HTTP и SignalR-тесты отклоняют запросы без JWT и с просроченным JWT. Активное соединение закрывается после истечения токена. При двух подключённых пользователях событие получает только адресат.
- [ ] **Хранилище и REST.** Модульные тесты проверяют кодирование и валидацию курсора. Интеграционные тесты с MongoDB проверяют стабильный порядок истории, счётчик, сохранение первого `readAtUtc` при повторе и `404` при попытке отметить чужое уведомление.
- [ ] **Consumer.** Интеграционный тест с MongoDB и RabbitMQ подтверждает сохранение записи до вызова Hub. После ошибки отправки и повтора в истории остаётся одна запись с исходным ID. Для отключённого клиента запись доступна через REST.
- [ ] **Ошибки и очередь.** При остановленном Notifications сообщение сохраняется в `notifications-ready-v1` до запуска потребителя. Интеграционный тест проверяет перенос сообщения после исчерпания повторов в `notifications-ready-v1_error` и успешное восстановление по тому же `notificationId`.
- [ ] **React и восстановление.** Тесты клиента проверяют сохранение настроек, объединение истории и повторных событий по ID, обновление счётчика и очистку состояния при выходе. Smoke-проверка на стенде подтверждает WebSocket через ingress и восстановление истории после перезапуска Notifications.
