# Notifications и React — план реализации

**Статус:** Notifications и React реализованы и проверены локально. Доставка через WebSocket за Vite и восстановление истории после перезапуска подтверждены. Внешний smoke остаётся до развёртывания [Ingress](../deploy/k8s/habit-tracker-ingress.yaml) на стенде. **Комплект:** этот файл + `plan/README.md` целиком.

**Границы:** новый Notifications backend и расширение существующего React. Worker готовит данные уведомления; этот сервис сохраняет их и доставляет. Не реализовывать scheduler, рассылку email или Web Push. Без исходников React подготовить новые компоненты и инструкции интеграции, а не заменять `App.jsx` целиком.

**Цель** — сохранять уведомления и доставлять их нужному пользователю через SignalR. Пользователь может восстановить пропущенные сообщения через историю.

**Основа** — [архитектура](README.md), [событие `NotificationReadyV1`](04-rabbitmq.md), [клиент React](../habit-frontend/src/). Создать `Auth/HabitTracker.Notifications` на ASP.NET Core .NET 8.

## Контракты для клиента

| Маршрут или событие | Контракт |
|---|---|
| `GET /api/notifications?limit=20&cursor={cursor}` | `{ items, nextCursor, unreadCount }`. `limit` от 1 до 100. Сортировка по `createdAtUtc` и ID по убыванию. Курсор кодирует оба поля последнего элемента |
| `PUT /api/notifications/{id}/read` | `204` при отметке и её повторе. `404` для отсутствующего или чужого уведомления |
| `/hubs/notifications` | Защищённое подключение SignalR. Серверное событие `NotificationReceived` содержит один DTO уведомления |

DTO содержит `id`, `kind`, `localDate`, `createdAtUtc`, `readAtUtc` и поля полезной нагрузки по виду уведомления. Напоминание передаёт `habitId` и `habitName`, сводка — `planned`, `completed`, `pending`. Текст формируется во фронтенде из этих полей. `unreadCount` относится ко всем уведомлениям владельца.

## Уточнения хранения, безопасности и доставки

### Сохранение события

В коллекции `notifications` хранить `_id=notificationId`, `userId`, `kind`, `localDate`, `createdAtUtc`, `readAtUtc=null`, полезную нагрузку. Для предсказуемой сортировки предлагается хранить UUID уведомления как каноническую lowercase строку формата `D`; не смешивать строковые и BSON UUID ID внутри коллекции. ObjectId владельца также приходит строкой.

Consumer проверяет ID, допустимый kind, форматы дат и обязательные поля вида. Ошибки контракта сразу идут в `_error`. Upsert по `_id` использует `$setOnInsert`: повтор не меняет исходный текст, время и readAtUtc. Затем прочитать **сохранённый** документ и вызвать `Clients.User(saved.UserId).SendAsync("NotificationReceived", dto, ct)`; не брать адресата из непроверенной повторной нагрузки. Конфликт одного notificationId с другим владельцем или видом — ошибка контракта, без доставки другому пользователю.

Если два consumer одновременно вставляют ID и один получает duplicate key, перечитать существующую запись и продолжить только после проверки совместимости. Нет необходимости в отдельном inbox: уникальность результата обеспечена notificationId. Сбой MongoDB не допускает вызов Hub. Сбой Hub после записи вызывает MQ retry с тем же ID. Отсутствие подключённых клиентов само по себе не ошибка.

ACK после записи и завершения вызова Hub не доказывает, что браузер показал сообщение. История обеспечивает восстановление; отдельного клиентского подтверждения доставки в этом этапе нет. Notifications имеет одну реплику со стратегией Recreate, иначе часть соединений без backplane не получит события.

### История и cursor

Предлагаемая точная схема cursor: base64url UTF-8 JSON `{ "v":1, "createdAtUtc":"...Z", "id":"UUID" }`. Это отдельный формат от ObjectId-cursor WebAPI. Проверить base64url, структуру, версию, дату UTC, UUID и ограничить размер строки, например 1024 символами. Ошибка — `400` ProblemDetails с `code=validation_error`. Cursor не даёт прав доступа: фильтр по текущему `sub` обязателен всегда.

Запрос MongoDB: `userId = sub` AND (`createdAtUtc < cursor.time` OR (`createdAtUtc = cursor.time` AND `_id < cursor.id`)), сортировка `createdAtUtc DESC, _id DESC`, взять `limit+1`. Вернуть первые limit; nextCursor последнего возвращённого элемента, если был дополнительный, иначе null. Индекс `(userId ASC,createdAtUtc DESC,_id DESC)`. `unreadCount` отдельным запросом по `userId` и `readAtUtc=null`; его значение отражает момент чтения, не обещать атомарный снимок с SignalR.

`PUT read` фильтруется по владельцу и ID, выставляет UTC только когда значение null. Повтор возвращает 204 с прежней датой. Если update ничего не изменил, отличить уже прочитанное своё уведомление от отсутствующего/чужого запросом с тем же owner-фильтром. Невалидный UUID — 400, неизвестный/чужой корректный — 404. Историю автоматически не удалять: срок её хранения пока не установлен.

### JWT и жизненный цикл Hub

Использовать те же `JwtSettings` из env, HS256, валидацию подписи/issuer/audience/срока и 24-символьного ObjectId в sub. `MapInboundClaims=false`, `IUserIdProvider` читает `sub`; одинаковое каноническое представление ID при авторизации и отправке. `[Authorize]` на контроллере и Hub. Query `access_token` принимается только на пути Hub и его транспортных подмаршрутах, не на REST. Включить закрытие соединения при истечении аутентификации.

Не создавать публичный метод `Send(userId, text)` в Hub. Публичный DTO не содержит владельца. Не логировать Authorization, access_token, URL query Hub, JWT key и тела аутентификации. При необходимости cross-origin перечислить разрешённый origin; целевой запуск через один reverse proxy использует same-origin.

## Поведение React

1. **Настройка привычки:** на странице существующей привычки загрузить GET reminder, показать «Напоминать о привычке» и `<input type="time">`. Время — местное время аккаунта, не браузера. Дни берутся из привычки, отдельного выбора дней нет. После PUT показать возвращённые сервером значения. Для новой привычки сначала сохранить саму привычку, затем на её странице отдельным запросом включить напоминание; ошибка настройки не отменяет создание привычки.
2. **Сводка:** отдельный блок с enabled и временем по аналогии; по умолчанию отключена и 21:00. Не придумывать профильный API для изменения timezone.
3. **Панель:** список от новых к старым, непрочитанные отмечены, кнопки «Загрузить ещё» и «Прочитано», состояния загрузки/пустого списка/ошибки с повтором. Текст строить из DTO безопасным JSX, без `dangerouslySetInnerHTML`. При архиве или недоступной привычке переход не должен ломать панель.
4. **Подключение:** зарегистрировать обработчик до `start()`, затем подключить JWT через accessTokenFactory. `withAutomaticReconnect` не заменяет повтор первого неудачного start: добавить отменяемый цикл. Повтор после 401/истечения JWT требует штатного входа, а не бесконечного reconnect с тем же токеном.
5. **Восстановление:** после подключения/переподключения запросить историю от начала. Для надёжного восстановления первого этапа выполнять отменяемый фоновый обход страниц до конца, объединяя по ID; первую страницу показывать сразу. Не останавливаться на первом знакомом ID: задержанный outbox может добавить уведомление с более старым createdAtUtc в середину истории. Для длинной истории в дальнейшем понадобится отдельный контракт синхронизации; произвольная отсечка сейчас теряет сообщения. Видимый список можно разбивать на страницы независимо от фоновой синхронизации.
6. **Объединение:** Map по id, повтор не увеличивает счётчик вручную. При merge не затирать уже известный readAtUtc значением null из старого события или ответа. Сортировать стабильно по времени и ID; событие и история могут прийти в обратном порядке.
7. **Счётчик:** после нового ID/успешного read инициировать refresh, объединять близкие запросы. Последовательно выполнять обновления или использовать номер запроса, чтобы старый ответ не перезаписал новый. После появления события во время запроса запланировать повторное обновление. Серверный unreadCount относится ко всем страницам, его нельзя вычислять только по видимому списку.
8. **Выход/смена аккаунта:** отменить HTTP и таймеры, удалить обработчики, stop Hub, очистить список и счётчик. Ответы старого сеанса игнорировать по идентификатору сеанса даже если отмена не успела. При StrictMode не оставлять второе соединение.

Сервис WebAPI при выключенном флаге возвращает 404 для настроек; UI сообщает о недоступности этой функции, а не подставляет «сохранено». Новые публичные REST-запросы использует тот же обработчик 401, что приложение.

Для Vite предлагается `NOTIFICATIONS_PROXY_TARGET=http://localhost:5162`. Добавить его загрузку явно: текущий `loadEnv(...,'API_')` не читает этот префикс. Проксировать `/api/notifications` раньше общего `/api`, `/hubs/notifications` с `ws:true`; остальные `/api` оставить WebAPI. В контейнерном Nginx и ingress сохранить тот же порядок и поддержку WebSocket.

## Тесты по этапам

- [x] **JWT и Hub.** HTTP и SignalR-тесты отклоняют запросы без JWT и с просроченным JWT. Активное соединение закрывается после истечения токена. При двух подключённых пользователях событие получает только адресат.
- [x] **Хранилище и REST.** Модульные тесты проверяют кодирование и валидацию курсора. Интеграционные тесты с MongoDB проверяют стабильный порядок истории, счётчик, сохранение первого `readAtUtc` при повторе и `404` при попытке отметить чужое уведомление.
- [x] **Consumer.** Интеграционный тест с MongoDB и RabbitMQ подтверждает сохранение записи до вызова Hub. После ошибки отправки и повтора в истории остаётся одна запись с исходным ID. Для отключённого клиента запись доступна через REST.
- [x] **Ошибки и очередь.** При остановленном Notifications сообщение сохраняется в `notifications-ready-v1` до запуска потребителя. Интеграционный тест проверяет перенос сообщения после исчерпания повторов в `notifications-ready-v1_error` и успешное восстановление по тому же `notificationId`.
- [x] **React и восстановление.** Тесты клиента проверяют сохранение настроек, объединение истории и повторных событий по ID, обновление счётчика и очистку состояния при выходе. Локальный smoke подтверждает WebSocket через Vite и восстановление истории после перезапуска Notifications.

## Проверяемые результаты и порядок сдачи

| Этап | Конкретный тест / результат |
|---|---|
| Модель, repository и cursor | 25 уведомлений, limit 20 → 20+5 без дублей; одинаковые timestamps правильно разделяются по ID; чужой cursor не открывает чужие данные |
