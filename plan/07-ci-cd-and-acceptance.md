# CI/CD и приёмка — план реализации

**Цель** — проверять каждый PR и доставлять проверенный коммит `main` на учебный стенд с возможностью отката.

**Основа** — [требования курса и архитектура](README.md), [развёртывание](05-deployment.md), [телеметрия](06-observability.md).

## Критерий готовности этапа backend

- [ ] В каждом PR добавить или обновить тесты затронутых этапов. Для бизнес-логики использовать xUnit с контролируемым временем и зависимостями. Для HTTP-контрактов, MongoDB-транзакций и RabbitMQ publisher/consumer проверять соответствующие интеграции. Перечни проверок приведены в планах [WebAPI](01-webapi.md), [Worker](02-worker.md) и [Notifications](03-notifications.md). Тестовая топология соответствует [спецификации RabbitMQ](04-rabbitmq.md).
- [ ] Запустить новые и существующие тесты. PR считается готовым после прохождения CI и проверки, что обязательные интеграционные тесты действительно выполнены. Покрытие измеряется по бизнес-логике всего backend, а сценарии каждого этапа проверяются отдельно.

## CI для PR и `main`

- [ ] Создать `.github/workflows/ci.yml` для `pull_request` и `push` в `main`. Использовать GitHub-hosted runner, версии .NET и Node из репозитория, восстановление NuGet и `npm ci` по lockfile.
- [ ] Выполнить `dotnet build Auth/WebApplication1.sln -c Release`, `dotnet format Auth/WebApplication1.sln --verify-no-changes --no-restore`, проверки Roslyn и `npm run lint` из `habit-frontend`. Выполнить `npm run build` и `npm test` там же.
- [ ] Пометить тесты с внешними зависимостями xUnit trait `Category=Integration`, в том числе существующие `MongoFact`. В CI перед интеграционным запуском поднять отдельный MongoDB replica set и RabbitMQ, дождаться readiness и передать `KONTUR_TEST_MONGO_URI` и настройки тестового брокера. Запустить `dotnet test Auth/WebApplication1.sln -c Release --filter "Category=Integration" --logger trx`. Проверять в TRX, что обязательные HTTP, MQ и MongoDB-тесты найдены, исполнены и прошли. Таймаут подготовки инфраструктуры завершает job ошибкой.
- [ ] Для модульных тестов запустить `dotnet test Auth/WebApplication1.sln -c Release --filter "Category!=Integration" --collect:"XPlat Code Coverage" --logger trx`. Собирать покрытие бизнес-логики WebAPI, Worker и Notifications, исключив сгенерированный код, startup, конфигурацию и DTO. Закрепить фильтры в runsettings. Суммарное покрытие строк бизнес-логики модульными тестами должно быть строго больше 60%. Публиковать покрытие и TRX в артефакты CI, проверять порог по исходным счётчикам покрытых строк без округления.
- [ ] После проверок выполнить Docker build четырёх образов. Для PR проверить сборку без публикации. Публикация выполняется только для проверенного коммита `main`. Сделать CI обязательной проверкой ветки.

## CD в Яндекс Облако

- [ ] Создать `.github/workflows/deploy.yml` после успешного CI для `main`, с идентификатором проверенного коммита. Собрать образы из этого коммита или использовать сохранённые образы CI. Опубликовать тег SHA в Yandex Container Registry, сохранить digest и передать их job развёртывания.
- [ ] Выполнять `kubectl` на выделенном self-hosted runner облачной VM. Runner запускает только доверенный workflow `main` и использует отдельный kubeconfig с правами на ресурсы приложения в `habit-tracker`. Облачные и Kubernetes-секреты создавать при bootstrap. Использовать GitHub Environment для настроек деплоя и ограничить параллельные выкладки одной на окружение.
- [ ] Применить манифесты с digest, дождаться rollout, проверить готовность pod и HTTPS. Запустить smoke-тест через публичный адрес с изолированным тестовым аккаунтом, проверить JWT, доступ к привычке и подключение Hub. При ошибке записать события кластера и журналы, развернуть предыдущий подтверждённый набор digest и снова проверить readiness.

## Матрица сценариев для спринтов

Для прогресса считать сценарий готовым после проверки на целевом стенде. Для спринта 3 показать 8 из 10 сценариев и доступное развёрнутое приложение, для спринта 4 довести до приёмки все десять. Строки таблицы задают рабочий перечень команды для требования PDF о готовности 75–80% сценариев в спринте 3.

| № | Сценарий | Что должно получиться |
|---|---|---|
| 1 | Регистрация и вход | JWT открывает защищённые маршруты |
| 2 | Создание и редактирование привычки | Список и расписание соответствуют сохранённым данным |
| 3 | Отметка и её отмена | Повтор запроса сохраняет одно логическое состояние |
| 4 | История и статистика | Данные соответствуют отметкам и расписанию |
| 5 | Архивирование | Привычка исчезает из активных и доступна в истории |
| 6 | Изоляция пользователей | Второй пользователь не читает и не меняет чужие записи |
| 7 | Настройка напоминания | Настройки сохраняются, Worker получает расписание |
| 8 | Уведомление в реальном времени | Для подходящей привычки один результат появляется у адресата через SignalR |
| 9 | Ежедневная сводка | Результат отражает состояние привычек на момент выполнения |
| 10 | Офлайн и восстановление | История после переподключения содержит пропущенное уведомление без дубля |

## Техническая приёмка и защита

- [ ] Запустить две реплики Worker, обработать одно задание и показать один сохранённый результат. Повторить с остановкой владельца lease и восстановлением другим экземпляром.
- [ ] Остановить брокер после запуска системы, изменить привычку, затем запустить брокер и проверить догоняющую публикацию. Повторить доставку одного ID, отправить poison message и показать `_error`.
- [ ] Сверить метрики HTTP, заданий и очередей, связать JSON-логи по `correlationId` и показать цепочку WebAPI → RabbitMQ → Worker → MongoDB в Jaeger. Показать вторую трассу для готового уведомления и вызова SignalR.
- [ ] На защите объяснить, где лежат данные, почему API отвечает до фоновой обработки, как Worker ждёт срока и что происходит при потере браузерного соединения. Показать Compose, манифесты k3s, успешный pipeline, покрытие и опубликованный стенд.
