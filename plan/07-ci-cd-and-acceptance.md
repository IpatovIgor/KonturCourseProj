# CI/CD и приёмка — план реализации

**Цель** — проверять каждый PR и доставлять проверенный коммит `main` на учебный стенд с возможностью отката.

**Основа** — [требования курса и архитектура](README.md), [развёртывание](05-deployment.md), [телеметрия](06-observability.md).

## Что уже есть

- [Текущий workflow](../.github/workflows/webapi-tests.yml) по имени `WebAPI tests` проверяет все три backend-проекта в Release. Он поднимает MongoDB replica set и RabbitMQ через тестовый Compose, ждёт готовности, проверяет bootstrap и replay RabbitMQ, запускает `npm ci`, тесты, линтер и сборку React. При сбое выводит логи зависимостей, а в конце удаляет тестовое окружение. Триггеры — PR с подходящими путями и ручной запуск.
- В трёх тестовых проектах установлен Coverlet. Dockerfile четырёх приложений и их контексты сборки уже заданы в [`compose.yaml`](../compose.yaml). Сборка Docker-образов в CI, проверка порога покрытия, публикация образов и облачная выкладка остаются задачами этого этапа.
- Наличие шагов подтверждено по YAML. Для подтверждения работы CI нужен успешный запуск в GitHub Actions со ссылкой на результат.

## CI для PR и `main`

- [ ] Расширить `.github/workflows/webapi-tests.yml` и использовать его как основной CI. Настроить запуск на все PR в `main` и на обновления `main`, сохранить ручной запуск и существующие проверки. Сделать результат CI обязательным для слияния PR.
- [ ] Добавить отдельную сборку `Auth/WebApplication1.sln` в Release, `dotnet format --verify-no-changes` и проверку настроек анализаторов Roslyn.
- [ ] Добавить `Category=Integration` для интеграционных тестов WebAPI с `MongoFact` и `RabbitFact`. Интеграционные наборы Worker и Notifications уже помечены. Разделить запуски unit и integration. Сохранить отдельную тестовую инфраструктуру и порядок запусков. Проверять в TRX, что обязательные тесты всех трёх сервисов найдены, выполнены и прошли.
- [ ] Для модульных тестов запустить `dotnet test Auth/WebApplication1.sln -c Release --filter "Category!=Integration" --collect:"XPlat Code Coverage" --logger trx`. Собирать покрытие бизнес-логики WebAPI, Worker и Notifications, исключив сгенерированный код, startup, конфигурацию и DTO. Закрепить фильтры в runsettings. Суммарное покрытие строк бизнес-логики модульными тестами должно быть строго больше 60%. Публиковать покрытие и TRX в артефакты CI, проверять порог по исходным счётчикам покрытых строк без округления.
- [ ] После тестов добавить Docker build четырёх образов из существующих Dockerfile с контекстами из `compose.yaml`. PR проверяет сборку, а публикацию запускает CD для проверенного коммита `main`.

## CD в Яндекс Облако

- [ ] Создать `.github/workflows/deploy.yml` после успешного CI для `main`, с идентификатором проверенного коммита. Собрать образы из этого коммита или использовать сохранённые образы CI. Опубликовать тег SHA в Yandex Container Registry, сохранить digest и передать их job развёртывания.
- [ ] Выполнять `kubectl` на выделенном self-hosted runner облачной VM. Runner запускает только доверенный workflow `main` и использует отдельный kubeconfig с правами на ресурсы приложения в `habit-tracker`. Облачные и Kubernetes-секреты создавать при bootstrap. Использовать GitHub Environment для настроек деплоя и ограничить параллельные выкладки одной на окружение.
- [ ] Применить манифесты с digest, дождаться rollout, проверить готовность pod и HTTPS. Запустить smoke-тест через публичный адрес с изолированным тестовым аккаунтом, проверить JWT, доступ к привычке и подключение Hub. При ошибке записать события кластера и журналы, развернуть предыдущий подтверждённый набор digest и снова проверить readiness.

## Артефакты и зависимости pipeline

| Создать / изменить | Назначение |
|---|---|
| `.github/workflows/webapi-tests.yml` | Дополнить существующие проверки сборкой solution, разделением unit и integration, отчётами и Docker build |
| `.github/workflows/deploy.yml` | Только успешный проверенный main SHA → registry → rollout → smoke/rollback |
| `Auth/coverage.runsettings` | Фильтры бизнес-логики, исключения startup/DTO/generated, формат покрытия |
| `scripts/check-test-results.ps1` или `.py` | TRX: обязательные наборы найдены, не skipped, успешны |
| `scripts/check-coverage.ps1` или `.py` | Числитель/знаменатель line coverage, строго >60 без округления |
| `scripts/smoke-test.ps1` или `.py` | Уникальный аккаунт, JWT, привычка, Hub и восстановление истории |
| `docs/ci-cd.md`, `docs/acceptance.md` | Переменные, артефакты, run URLs, результаты десяти сценариев и откат |

Новые скрипты возвращают ненулевой код при провале и печатают причину. TRX, покрытие и логи сохранять при любом результате, исключая секреты из артефактов.

### Предлагаемый граф CI

```text
checkout verified source
 ├─ backend restore → build/format/analyzers → unit + coverage gate
 ├─ frontend npm ci → lint → test → build
 └─ isolated Mongo replica set + Rabbit topology → integration + TRX gate
все обязательные проверки успешны → Docker build четырёх образов
main, тот же SHA → publish digests → deploy → readiness + smoke
```

Текущий runner использует Linux, .NET 8 и Node.js 24. Сохранить соответствие SDK в `global.json`, Node.js в Dockerfile фронтенда и зависимостям в lockfile.

`dotnet format --verify-no-changes` в старом проекте может обнаружить существующее форматирование. Не отключать проверку автоматически и не включать массовый форматирующий diff в функциональную задачу: отдельно согласовать и выполнить приведение или явно зафиксировать временную область проверки. Roslyn должен реально работать в build, наличие названия шага не доказывает анализ.

### Интеграционная инфраструктура

WebAPI и Notifications используют [`compose.webapi-tests.yaml`](../compose.webapi-tests.yaml) и `KONTUR_TEST_*` по [инструкции](../docs/webapi-testing.md). Сохранить последовательный прогон этих наборов на общем брокере. `RabbitOutboxTests` временно блокирует подключения к тестовому vhost. Worker поднимает отдельные MongoDB и RabbitMQ через Testcontainers. При разделении CI на jobs поднимать зависимости в том job, где выполняются соответствующие интеграционные тесты. Сохранить проверку готовности и очистку тестовой инфраструктуры с `always()`.

Обязательный TRX gate проверяет как минимум наличие и успешность групп WebAPI HTTP/Mongo/MQ, Worker consumer/bootstrap/lease/outbox, Notifications REST/Hub/consumer. Зафиксировать список ожидаемых тестов или групп в версионируемом manifest; если имя изменилось, обновить manifest в том же PR. Проверка лишь `total > 0` пропустит отсутствие целого сервиса. Любой skipped обязательного сценария и отсутствие TRX — провал. Trait `Category=Integration` должен быть у новых и существующих интеграционных тестов до включения фильтра.

### Покрытие

Unit прогон: `dotnet test Auth/WebApplication1.sln -c Release --filter "Category!=Integration" --collect:"XPlat Code Coverage" --settings Auth/coverage.runsettings --logger trx`. Измерять бизнес-логику: календарь, правила eligibility/состояний, преобразования и валидацию, где они относятся к поведению; исключения перечислить явно в runsettings, не исключать сложные классы ради процента.

Объединить отчёты по уникальным исходным файлам/строкам, не суммировать одну и ту же библиотеку повторно из нескольких test assemblies. Gate: `coveredLines * 100 > totalLines * 60`; totalLines=0, отсутствующий или непарсируемый отчёт — ошибка. Ровно 60% не проходит. Интеграционное покрытие может собираться отдельно, но не добавляется к числителю требования **unit >60%**.

## Доставка только проверенного коммита

Предложенные имена параметров окружения: `YC_REGISTRY_ID`, `K8S_NAMESPACE=habit-tracker`, `APP_BASE_URL`; секреты registry push и kubeconfig задаются через GitHub Environment/на доверенном runner. Формат credentials определяется выбранным способом аутентификации облака; не вставлять реальный JSON-ключ в YAML. Pull credential кластера отдельный от push credential workflow.

- В PR jobs достаточно `contents: read`, без cloud secrets. Не выполнять недоверенный код pull request на self-hosted runner и не использовать `pull_request_target` для запуска кода из fork с секретами.
- Если deploy запускается через `workflow_run`, проверить conclusion success, исходную ветку main, доверенный репозиторий и checkout именно `head_sha` завершённого run. Нельзя взять текущую вершину main вместо проверенного SHA.
- Публиковать образы `webapi`, `worker`, `notifications`, `frontend`, помеченные SHA; сохранить manifest SHA → четыре digests как артефакт выпуска. Если сборка повторная, снова из того же SHA, с закреплёнными входными зависимостями.
- Одна выкладка на environment одновременно. Bootstrap и применение конфигурации выполняются в явном kube context/namespace. Сохранить предыдущий успешный набор digests до изменения Deployment.
- Сначала совместимые topology/consumers, затем publishers/UI. Дождаться rollout каждого приложения и health; smoke обращается к внешнему HTTPS адресу.
- При ошибке снять диагностику без секретов, подготовить данные по [инструкции отката](05-deployment.md#откат-на-версию-до-спринта-3), если целевые образы выпущены до спринта 3, вернуть весь предыдущий комплект приложений и проверить readiness и smoke. При ошибке первого deploy остановить выпуск и сохранить диагностику.

## Сценарий smoke и данные для демонстрации

Smoke создаёт пользователя с уникальным email запуска и привычку с расписанием, включающим текущий местный день. JWT получает через реальный login. Ключ Worker не передаётся браузеру. После проверки технический аккаунт не удаляется неподдерживаемым API: для локальной изолированной БД очистка по fixture, на стенде — согласованная процедура команды.

Для проверки задать напоминание при создании или правке привычки и перечитать настройки через GET. Срок выбрать с запасом по часовому поясу аккаунта и интервалу опроса Worker. В локальном Compose он составляет 5 секунд. При запуске около полуночи пересчитать дату и срок после смены суток. Автоматические тесты календарных правил используют `TimeProvider`, а smoke работает по обычным часам стенда.

Проверка Hub должна включать подключение, получение сообщения адресатом и отсутствие его у другого аккаунта. Одного ответа negotiate 200 недостаточно для доказательства WebSocket Upgrade через ingress. Отдельно закрыть соединение, сформировать уведомление, подключиться и получить запись через историю с прежним ID. Проверить повтор read и unreadCount.

Для сценариев таблицы 1–10 оформить `docs/acceptance.md`: номер, commit SHA, окружение/URL, время проверки, шаги, ожидаемый/фактический результат, ссылка на тест/артефакт. 8/10 — готовность спринта 3 только при реально развёрнутом стенде; локальные заглушки не закрывают облачную приёмку.

## Проверка самого CI/CD и критерий готовности

1. Проверить синтаксис workflow и скрипты локально доступными валидаторами; затем запустить настоящий PR workflow.
2. На отдельном тестовом изменении убедиться, что падающий тест, skipped обязательной интеграции, отсутствующий отчёт и покрытие ровно 60% действительно делают pipeline красным. Не оставлять намеренно падающие изменения в рабочем PR.
3. Убедиться, что PR не публикует образы и не получает секреты, main выпускает только прошедший проверки SHA, два выпуска не перемешиваются.
4. На тестовом окружении проверить неуспешный smoke и восстановление предыдущих digests; логи сбоя и rollback доступны в артефактах.
5. Приложить ссылки на CI run, coverage/TRX, manifest образов, успешный deploy и заполненную матрицу приёмки.

**Готовность подтверждают** обязательный CI в GitHub Actions, отчёт с покрытием выше 60%, публикация четырёх образов проверенного коммита и успешные проверки выкладки и отката на целевом стенде.
