# Worker — план реализации

**Статус:** Worker интегрирован в solution и запускается в GitHub Actions. В локальной сквозной проверке второй процесс Worker подхватил задание после остановки первого владельца и истечения lease. [Запуск и настройка](../docs/worker.md). **Комплект для исполнителя:** этот файл + `plan/README.md` целиком. Полные C#-контракты, HTTP JSON, топология, API общих библиотек и тестовое окружение находятся в README.

**Результат:** отдельный ASP.NET Core-сервис `HabitTracker.Worker`, его тесты, конфигурация и инструкции подключения к solution. Не создавать заново WebAPI, Contracts и Messaging. Не реализовывать SignalR, UI и REST-историю уведомлений в Worker.

**Цель** — по расписанию формировать напоминания о привычках и ежедневные сводки, восстанавливать незавершённые задания после перезапуска.

**Основа** — [архитектура](README.md), [внутренние маршруты WebAPI](01-webapi.md), [контракты RabbitMQ](04-rabbitmq.md). Создать `Auth/HabitTracker.Worker` на ASP.NET Core .NET 8 с MassTransit и `BackgroundService`. Использовать `TimeProvider` для правил календаря и тестов.

## Данные

| Коллекция | Что хранится и как читается |
|---|---|
| `habitSchedules` | Снимок по `habitId`, последняя версия, владелец, часовой пояс, расписание, время напоминания и `nextDueAtUtc`. Индекс `nextDueAtUtc, _id` |
| `summarySchedules` | Снимок по `userId`, версия, часовой пояс, настройки сводки и `nextDueAtUtc`. Индекс `nextDueAtUtc, _id` |
| `jobs` | `_id` UUID, `kind`, `userId`, `habitKey`, `localDate`, `scheduleRevision`, `dueAtUtc`, `status`, `attempts`, `lastUpdated`, `leaseOwner`, `leaseUntil`, `leaseVersion`. Уникальный индекс `(userId, kind, habitKey, localDate)`, индексы `(status, dueAtUtc, _id)` и `(status, leaseUntil, _id)` |
| `inboxEvents` и `outboxEvents` | ID обработанного события и события для публикации. Индексы и правила отправки из [спецификации RabbitMQ](04-rabbitmq.md) |

`habitKey` равен ID привычки или пустой строке для сводки. Статусы задания — `pending`, `running`, `completed`, `skipped`, `failed`. Сохранённый ID задания используется как `notificationId`. Завершённое задание предотвращает повторное уведомление того же вида за дату. Результат `skipped` фиксирует условия на момент исполнения, последующая отмена отметки не порождает повторного напоминания за день.

### Детали документов и конкурентных операций

- `_id` расписания привычки = строковый `habitId`, `_id` сводки = строковый `userId`. Хранить все поля HTTP-снимка из README, `nextDueAtUtc` (nullable UTC) и `nextLocalDate` (nullable строка). Дополнительно сохранять корреляцию и trace context последнего применённого события. При загрузке из HTTP без события создавать контекст bootstrap.
- `revision` сравнивать только внутри одного расписания: применить, если запись отсутствует или входная версия строго больше. Равная и меньшая версия не меняют данные, срок или контекст. Для отсутствующего документа допустима версия 0 старого аккаунта. Не использовать безусловный upsert, который при провале фильтра версии пытается вставить второй `_id`.
- Consumer в одной транзакции: проверить/добавить inbox `_id=eventId`, применить снимок и commit. Дубликат inbox означает успешную ранее выполненную обработку. Старое, но впервые полученное событие записать в inbox без изменения расписания. Ошибка после записи inbox должна откатить и inbox, и расписание.
- `inboxEvents`: UUID `_id`, `processedAtUtc`, тип события. На первом этапе без TTL: очистка inbox требует отдельно согласованного окна replay. Это не outbox, политика удаления опубликованных сообщений к inbox не применяется.
- В `jobs` дополнительно хранить `timeZoneId`, `httpFailureCount`, `lastErrorCode` и контекст трассировки. `attempts`, `leaseVersion`, `httpFailureCount` начинаются с 0. `kind` совпадает со значениями `NotificationReadyV1.Kind`. BSON UUID хранить в Standard representation. Не сохранять токены или полные ошибочные HTTP-тела.
- Терминальные `completed`, `skipped`, `failed` автоматически не открывать заново. Планировщик при конфликте уникального ключа оставляет их без изменения. Смена настроек или новая revision не создаёт второе задание за тот же день. Уникальный ключ намеренно **не включает** revision.
- Планировщик не меняет `running` и его lease. Обновление существующего `pending` допускается с проверкой его текущего статуса; не сбрасывать счётчик временных HTTP-сбоев и не сокращать уже установленную задержку повтора. Проверка актуальности перед отправкой разрешает перенос на более позднее время.
- Таблица `bootstrapState`: постоянный ID, например `initial-schedules-v1`, состояние завершения и время. Маркер записывается только после полного обхода **обоих** потоков страниц. Частичный обход не делает Worker готовым.

Индексы создавать идемпотентно до readiness. В фильтрах `nextDueAtUtc <= now` явно исключить null. При транзакционной гонке повторять операцию с новым чтением; при duplicate key повторно прочитать победивший документ, не маскировать любую ошибку MongoDB как дубликат.

## Алгоритмы, которые должны совпасть у всех реализаций

### 1. Bootstrap и события

1. Инициализировать MongoDB и индексы, затем подключить consumer.
2. Если успешной загрузки ещё не было либо запрошена принудительная перезагрузка, начать с первой страницы привычек и затем сводок. Передавать `nextCursor` в `after`; закончить на null.
3. Каждый снимок применять через тот же projector и сравнение revision, что события. HTTP-пагинация не замораживает всю базу: пришедшее событие v8 не должно быть затёрто страницей v7.
4. После ошибки HTTP/MongoDB не ставить marker complete; повторить обход с первой страницы с задержкой. При сетевом сбое consumer продолжает сохранять доступные события. При `401/403` вывести диагностическую ошибку конфигурации без ключа, readiness оставить false; не продолжать с пустыми расписаниями.
5. После двух успешных обходов сохранить marker, разрешить планирование и исполнение заданий. Обычный restart с готовым marker продолжает работу с сохранёнными расписаниями и накопленными сообщениями.

Предлагаемый параметр `Worker__ReloadSchedulesOnStartup=false` принудительно повторяет обход при запуске. После периода `Features__NotificationsEnabled=false` остановить все реплики Worker, включить WebAPI, запустить реплики с этим параметром true, дождаться завершения и вернуть false при последующем штатном запуске. При принудительной перезагрузке каждый запущенный процесс должен пройти свой барьер загрузки; старый marker сам по себе не разрешает ему начать планирование. Не удалять расписания, jobs или inbox для перезагрузки.

Две одновременно загружающиеся реплики допустимы: операции идемпотентны. Загрузка страниц не должна сбрасывать указатели расписаний при равной версии. В сценарии смены БД или восстановления из backup выполнять отдельную согласованную процедуру, не трактовать неполный HTTP-обход как команду удалить локальные записи.

### 2. Следующий срок и выдача задания

`ScheduleCalculator` возвращает пару `(localDate, dueAtUtc)` либо отсутствие срока. Удобный интерфейс: `NextHabitDue(snapshot, now, afterLocalDate)` и `NextSummaryDue(snapshot, now, afterLocalDate)`, где `afterLocalDate` — исключительная нижняя граница уже обработанного дня. Это предлагаемые внутренние методы; их типы определить явно в коде.

- Начать с текущего местного дня (или следующего за `afterLocalDate`, если он позже). Дни до текущего местного дня не создавать.
- У активной включённой привычки найти ближайшую дату не раньше startDate с подходящим днём применимой scheduleVersion. У включённой сводки подходит каждый день.
- Если срок **сегодня уже прошёл**, вернуть сегодняшний срок в прошлом: это одно догоняющее уведомление за сегодня. Нельзя всегда искать только `dueAtUtc > now`, иначе restart после 20:00 теряет сегодняшний день.
- Выключенный/архивный снимок сохранять с `nextDueAtUtc=null` и `nextLocalDate=null`, включая его revision: удаление документа позволило бы старому событию оживить расписание.
- После выдачи задания вызвать расчёт с `afterLocalDate=дата выданного задания`, чтобы указатель ушёл на следующий подходящий день. При простое повторно рассчитать от сегодняшнего дня, не выдавая накопленные дни прошлого.

В одной транзакции: прочитать просроченное расписание, создать/условно обновить задание, сдвинуть указатель с фильтром по `_id`, revision и старому `nextDueAtUtc`. Если CAS сдвига не прошёл — откатить всю транзакцию. Нельзя сохранить задание, рассчитанное по проигравшей версии. Конфликт уникального ключа терминального задания не мешает продвинуть указатель дальше.

Пачки ограничены; после обработки пачки можно взять следующую, проверяя отмену и не держа бесконечную транзакцию. HTTP и RabbitMQ-публикацию внутрь MongoDB-транзакции не включать.

### 3. Lease и таблица переходов задания

| Исходное состояние / результат | Следующее состояние | Действие |
|---|---|---|
| `pending`, `dueAtUtc <= now` | `running` | Атомарный захват, новый owner, `leaseVersion++`, `attempts++`, lease 2 минуты |
| `running`, lease истёк | `running` нового владельца | То же; старый owner теряет право завершения |
| `running`, eligibility true | `completed` | В одной транзакции завершить и вставить outbox |
| `running`, `404` или обычный eligibility false | `skipped` | Зафиксировать причину, без outbox |
| `running`, `notDueYet` | `pending` | Перенести на `nextDueAtUtc`, освободить lease; HTTP failure count не увеличивать |
| `running`, временный сбой №1–4 | `pending` | Счётчик HTTP-сбоев +1, задержка 1/2/4/8 минут соответственно |
| `running`, временный сбой №5 | `failed` | Без outbox; безопасный код диагностики |
| `running`, прочие `4xx` | `failed` | Ошибка контракта/ключа; без бесконечного retry |
| `running`, наступил другой местный день | `skipped` | Не отправлять вчерашнее уведомление |
| Любой результат после потери lease | Без изменения | Прекратить работу, не писать outbox |

Все переходы из `running` и продление фильтруются по `_id`, `status=running`, `leaseOwner`, `leaseVersion`, `leaseUntil > now`. Проверить matched count. Нулевой результат — потеря владения, а не успешное завершение. Owner уникален для запуска процесса, не только имя машины.

Продлевать lease раз в 30 секунд параллельно исполнению. Если продление не удалось, отменить HTTP/обработку через связанный CancellationToken. Даже если отмена опоздала и HTTP вернулся, финальный CAS не позволит бывшему владельцу записать результат. Продление во время завершения может вызвать write conflict — транзакцию нужно корректно повторить или прекратить после потери владения.

### 4. HTTP-проверка и завершение

Перед запросом проверить местную дату по текущему известному расписанию; перед завершением после долгого запроса проверить её снова. Дата запроса всегда равна `job.localDate`. Не отправлять уведомление за вчера, если HTTP пересёк местную полночь.

Временными считаются таймаут, сетевой сбой, `429`, `5xx`. Не добавлять автоматические retries HttpClient поверх таблицы: иначе пять учитываемых попыток превратятся в неизвестное число реальных запросов. Остановка приложения/потеря lease не считается HTTP-сбоем. Невалидный JSON, несовместимая схема, `notDueYet` без валидного срока — ошибка контракта с `failed`, без создания уведомления. Если перенос или backoff пересекает местную дату задания, завершить `skipped`.

На успешном ответе напоминания брать `habitName` и revision из ответа. На сводке брать три счётчика; не пересчитывать их из своей копии расписаний. В транзакции выполнить fenced update задания и `MongoOutbox.InsertAsync(session, notification, context, ct)`; при потере lease либо ошибке outbox откатить всё. UUID события сформировать один раз для логической транзакционной операции, не генерировать новый на повтор публикации.

`NotificationId = job.Id`; `HabitId = job.HabitKey` только для напоминания. Поля чужого вида оставить null. Завершённое задание означает сохранённый результат/outbox, а не подтверждение доставки в браузер. Publisher работает независимо и переживает простой RabbitMQ.

## Конфигурация Worker

Помимо общей таблицы env из README определить и валидировать следующие **новые параметры**. Это предлагаемые значения первого этапа, не уже существующая конфигурация:

| Параметр | Значение по умолчанию |
|---|---|
| `Worker__PollIntervalSeconds` | 60; период поиска расписаний и доступных jobs |
| `Worker__BatchSize` | 100; от 1 до 200, также размер страницы bootstrap |
| `Worker__LeaseSeconds` | 120 |
| `Worker__LeaseRenewalSeconds` | 30; меньше LeaseSeconds |
| `Worker__HttpTimeoutSeconds` | 10 |
| `Worker__BootstrapRetrySeconds` | 5; отменяемая задержка после временного сбоя |
| `Worker__ReloadSchedulesOnStartup` | false |

На первом этапе достаточно последовательного исполнения заданий внутри процесса и двух процессов для проверки конкуренции. Не создавать неограниченное число Tasks. Реальная задержка отправки включает polling, обработку очереди и сеть; точность до секунды не обещается.

При старте валидировать MongoDB, RabbitMQ и WorkerApi URL/key. Секреты не иметь в appsettings. `/health/live` отвечает без доступа к зависимостям; `/health/ready` возвращает 503 до индексов, готовности consumer и bootstrap, а также при недоступности обязательных зависимостей. Подготовить точки логирования `jobId`, `kind`, перехода, `correlationId`, длительности; общую систему экспорта подключает этап телеметрии.

После изменения настроек пересчитывать ближайший срок. Перед исполнением повторно учитывать актуальные настройки, поэтому устаревшее задание не отправит уведомление раньше нового времени.

Lease на две минуты, продление каждые 30 секунд. Продление, перенос и завершение используют фильтр по ID, владельцу, версии, статусу и непросроченному lease. Потеря lease отменяет обработку, следующий владелец может подобрать задание.
- [x] Запросить актуальное состояние через WebAPI. При `404`, архиве, выключенном напоминании, отметке, неподходящем дне или смене местной даты завершить `skipped`. Для `notDueYet` использовать `nextDueAtUtc` как новый срок и вернуть `pending`. Перенос по расписанию не расходует лимит повторов HTTP. При таймауте, `429` и `5xx` вернуть `pending` с задержкой 1, 2, 4, 8 минут, после пятого временного сбоя — `failed`. Счётчик таких сбоев хранить отдельно от `attempts`, который считает захваты. Повторы прекращаются при смене местной даты. Остальные `4xx` переводят задание в `failed` и фиксируются в диагностике.
- [x] Для подходящего задания в одной MongoDB-транзакции изменить `running` на `completed` и записать `NotificationReadyV1` в outbox. Проверить актуальность lease в фильтре перед записью. Поля уведомления берутся из последнего ответа API. Изменение привычки после этой проверки относится к следующей обработке. Передать корреляцию и трассировку через outbox.
- [x] Подключить механизм отправки outbox с собственной коллекцией Worker. Публиковать `NotificationReadyV1` в `notification-ready-v1` после коммита задания. При сбое публикации готовый результат остаётся в outbox до подтверждения брокера.

## Тесты по этапам

- [x] **Consumer и начальная загрузка.** Интеграционные тесты с RabbitMQ и MongoDB проверяют повтор события, поступление старой версии и откат транзакции при ошибке. Тест начальной загрузки подаёт новое событие между страницами снимков и подтверждает, что старый снимок не перезаписывает его. После сбоя загрузка повторяется, задания выдаются после её завершения.
- [x] **Ошибки потребления.** Интеграционный тест проверяет retry временного сбоя, перенос poison message в `worker-habit-events-v1_error` и неизвестного типа в `worker-habit-events-v1_skipped`. Повтор исправленного сообщения из DLQ даёт одну запись inbox.
- [x] **Календарь.** Модульные тесты с фиксированным временем проверяют разные пояса, местную полночь, оба перехода DST, будущую версию расписания и пропуск дней до текущей местной даты.
- [x] **Создание заданий.** Интеграционный тест одновременно запускает два цикла планирования. За один местный день появляется одно задание, указатель расписания продвигается. Сбой транзакции оставляет прежний указатель и позволяет повторить обработку.
- [x] **Захват и lease.** Интеграционные тесты с двумя экземплярами подтверждают одного владельца активного lease, продление, повторный захват после истечения и отказ завершения устаревшим владельцем.
- [x] **Проверка через API.** Тесты с подменой HTTP и часов проверяют пропуск выполненной или архивной привычки, перенос срока, пустую сводку, повтор при `429`, `5xx` и таймауте, переход в `failed` после лимита и прекращение повторов при смене местной даты.
- [x] **Результат и публикация.** Интеграционный тест на replica set имитирует ошибку записи outbox и проверяет откат завершения. После повторного захвата и восстановления Worker RabbitMQ получает один логический `NotificationReadyV1` с неизменным `notificationId`.
